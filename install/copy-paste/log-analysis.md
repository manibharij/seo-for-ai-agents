# Log-file & Crawl-budget Analysis — copy-paste mini (paste this into your AI coding agent)

*Self-contained version of the log-analysis skill. Advanced, large-site: see what crawlers actually fetch from your server logs.*

> ⚠️ **Experimental, and run by an AI agent — which can make mistakes.** Logs are sensitive (IPs/PII) — never commit them or paste raw logs into a chat. See the repo's `DISCLAIMER.md`.

---

You are analysing my server or CDN access logs to see what crawlers **actually fetch**: important pages they ignore and crawl budget wasted on junk. This needs my own logs (my data) and matters mainly for **large sites**. Work in four steps: Diagnose, Fix, Verify, Report.

## Inputs and modes
**Mode.** Default to `audit`: analyse the logs and record findings, and change nothing on the site. In `fix` mode, apply only the findings I approve (by id, or a rule such as "all low-risk"), on a git branch where one exists, and verify each on the served output. In `re-check` mode, run the identical pipeline on a new log window of the same length and tell me what is fixed, what regressed and what changed. Running unattended never widens `fix` beyond low-risk, reversible items. Ask like this: "Run log analysis in fix mode: apply L-02", or "Run log analysis in re-check mode on logs/2026-11/".

Infer the rest before starting; ask only if a wrong guess would be costly. **Access:** URL only, read-only repo, or write access (without write access, fixes become precise instructions). **Tools:** a rendering browser, then `curl` / `Invoke-WebRequest`, then a fetch tool (never for headers). **Scope:** whole site, a section, or a stated budget; stop when it is spent. **Audience:** terse and evidence-first for specialists; explain why for everyone else. **Output:** chat report by default; `.seo/` state, CSV or tickets when asked. **Context:** read `.seo/context.md` if it exists for key sections and money pages; only `[established]` facts may reach copy, markup or trust signals.

## Step 1: Diagnose (get logs and identify crawlers)
- **Is budget the question?** Google's crawl budget guide targets sites with 1M+ pages changing weekly, 10k+ changing daily, or many "Discovered - currently not indexed" URLs. Below that, use logs for errors and AI-crawler activity and say budget is unlikely to be the bottleneck.
- **Get logs:** at least two weeks, ideally 30 days; prefer CDN edge logs if a CDN caches pages. Work locally, `.gitignore` the log folder, store only aggregates.
- **Parse** to `ip, uri, status, ua`. Combined format: `awk -F'"' 'tolower($6) ~ /googlebot/ { split($1,a," "); split($2,r," "); split($3,s," "); printf "%s,%s,%s\n", a[1], r[2], s[1] }' access.log > googlebot-claims.csv`. Cloudflare JSON lines: `gunzip -c logs/*.json.gz | jq -r 'select(.ClientRequestUserAgent | test("googlebot"; "i")) | "\(.ClientIP),\(.ClientRequestURI),\(.EdgeResponseStatus)"' > googlebot-claims.csv`. On Windows or for big files, load either format into DuckDB (`read_csv` with `regexp_extract` for combined logs, `read_json(..., format = 'newline_delimited')` for JSON).
- **Verify crawlers; never trust the user agent.** For each distinct IP: reverse DNS, check the name ends in `googlebot.com`, `google.com` or `googleusercontent.com` (Bing: `search.msn.com`), then forward-resolve that name and confirm the same IP. Bash: `host 66.249.66.1` then `host crawl-66-249-66-1.googlebot.com`. PowerShell: `(Resolve-DnsName 66.249.66.1 -Type PTR).NameHost`, then `(Resolve-DnsName <name>).IPAddress`. For many IPs, match against published ranges instead: Google's JSON files (e.g. `https://developers.google.com/static/crawling/ipranges/common-crawlers.json`), `https://www.bing.com/toolbox/bingbot.json`, and OpenAI's per-bot files (`https://openai.com/gptbot.json`, `searchbot.json`, `chatgpt-user.json`). Bucket hits: verified search crawlers, verified AI crawlers, other bots, spoofers, humans. Reason only from verified buckets.
- **Analyse verified hits:** crawl share by section and status, written as CSV `section,status_class,hits,share_pct` (parameter URLs as their own `parameter` section); sitemap URLs with zero hits and the last crawl date of the rest; the most-hit parameter, redirect and error URLs; frequency against importance; the AI-crawler mix.
- **URLs the site never made:** verified crawler hits returning `200` on paths that match no template and aren't in the sitemap (random or spam-like paths) can mean injected pages. Tell me, and compare one as a browser and as Googlebot. A big spoofer bucket is a security note too.
- **Optional live-data joins:** look for a tool in your environment first, then an API with my own credentials (environment variables, checked by name, never printed), then an export I give you. Search Console URL Inspection (`POST https://searchconsole.googleapis.com/v1/urlInspection/index:inspect` with `inspectionUrl` and `siteUrl`, read-only scope, 2,000 calls a day per site) gives `lastCrawlTime` and `coverageState` for a sample of uncrawled key URLs; Search Analytics clicks by page let you weight waste by real traffic. Without either, the logs stand alone; say what was skipped.
- **No logs?** Use Search Console, **Settings > Crawl stats** (root-level properties; last 90 days; by response, file type, purpose and Googlebot type, plus host status), with the Page indexing report filtered to a sitemap. Neither report has an API, so read them from a tool that covers them or from my export or screenshot. Record the figures with the date as the baseline, and say the analysis is coarser.

## Step 2: Fix (recommend, and apply what is in scope)
- **Low-risk in `fix` mode** (with write access and approval; small and reversible): update internal links that point at redirects or `404`s; remove redirects, `404`s and non-canonical URLs from the sitemap.
- **Ask first:** soft 404s to real `404`/`410`; collapsing redirect chains (migrations); stopping crawlable links to low-value filter combinations and adding `robots.txt` blocks for them. Test any `Disallow` against the sitemap URL list first. `noindex` does not save crawl budget (Google still fetches the page), but a robots-blocked URL cannot show its `noindex`, so let indexed URLs drop out before blocking. Treat existing rules as possibly intentional.
- **Recommend:** link under-crawled key pages from strong pages and cut click depth (Connect); fix `5xx`/`429`/slow responses (Google crawls less when a site struggles).
- Record findings in `.seo/` with these fields: `id`, `skill`, `area`, `target`, `severity`, `evidence`, `fix`, `risk`, `status` (`open` / `fixed` / `regression` / `needs-human` / `wont-fix`), `verified` (ISO date), `notes`.

## Step 3: Verify (re-sample after fixes)
Confirm the served `robots.txt`, statuses, links and sitemap show the fix. Then wait (two to four weeks is a reasonable minimum), pull a new window of the same length, run the identical pipeline, and compare before and after crawl-share CSVs and the coverage of key URLs. Mark findings `fixed` when waste fell and key URLs gained hits, `regression` if a fixed pattern returns, or leave `open` if the window is too short. Note other changes in the window; don't claim causation from one comparison.

## Step 4: Report
What crawlers are really doing (e.g. "verified Googlebot spends 41% of requests on filter URLs; 30% of product pages weren't crawled in 30 days"), the waste and gaps, the fixes with owners, what you applied, the before and after once re-sampled. **Boundary:** a point-in-time read of the logs I gave you; ongoing monitoring is continuous work, and rankings impact is live data. Record conclusions (not raw logs or IP lists) in `.seo/`.
